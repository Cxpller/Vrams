# Product Analysis Skill

## Purpose

以产品经理的视角，分析 VRAMS 项目的需求，输出结构化的产品文档。

适用场景：
- 用户提出模糊需求时，帮助澄清和细化
- 新功能规划前，输出 PRD
- 现有功能复盘，提出改进方案

## Workflow

### Step 1: 需求收集 & 澄清

当用户提出需求时，依次明确以下问题：

| 问题 | 目的 |
|------|------|
| 这个功能解决什么**问题**？ | 确认痛点和动机 |
| 谁是**目标用户**？ | 确定用户画像（本科生/研究生/导师/管理员） |
| 期望的**核心价值**是什么？ | 衡量功能是否成功 |
| 有没有**优先级**或**截止时间**？ | 确定投入力度 |

若需求描述模糊，先追问澄清，不要直接跳到方案。

### Step 2: 竞品分析

查询同类产品做法（如有必要）：

- 文献管理：Zotero / Mendeley / EndNote
- 桌面笔记：Obsidian / Notion / Logseq
- 论文辅助：LaTeX 编辑器 / Overleaf / 知网

对比维度：功能覆盖、交互体验、技术方案、优劣势。

### Step 3: 编写 PRD（产品需求文档）

输出以下结构：

```
# PRD: <功能名称>

## 1. 背景与目标
- 业务背景
- 要解决的核心问题
- 成功指标（如何衡量上线效果）

## 2. 用户故事
作为 <角色>，我希望 <功能>，以便 <价值>。

## 3. 功能列表
### P0 — 必须（MVP）
- [ ] 功能 A
- [ ] 功能 B

### P1 — 重要
- [ ] 功能 C

### P2 — 锦上添花
- [ ] 功能 D

## 4. 交互流程
- 用户操作路径（正常流程）
- 异常流程与边界处理

## 5. 非功能需求
- 性能要求
- 安全要求
- 兼容性要求

## 6. 数据模型（可选）
核心实体与字段

## 7. 约束与限制
- 技术约束
- 业务约束
- 待确认事项（Open Issues）
```

### Step 4: 需求评审

PRD 完成后，从以下维度自检：

- **必要性**: 不做会怎样？能否砍掉？
- **可行性**: 现有架构/资源是否能支撑？
- **一致性**: 是否与 VRAMS 已有功能冲突或重复？
- **可测性**: 上线后如何验证功能正常？
- **ROI**: 开发成本 vs 用户价值是否合理？

### Step 5: 输出开发建议

给技术团队（也就是 Claude）的输出：

- 建议优先实现的功能（按 P0 → P1 → P2 顺序）
- 建议分几期迭代，每期范围
- 需要提前确认的技术预研点
- 参考 [[development-standard]] 中相关规范

## Output Format

最终产出为以下 Markdown 格式：

```markdown
# PRD: [功能名称]

**版本**: v1.0
**日期**: YYYY-MM-DD
**状态**: 草稿 / 评审中 / 已定稿

---

## 1. 背景

...

## 2. 用户故事

...

## 3. 功能列表

| 优先级 | 功能 | 说明 |
|--------|------|------|
| P0 | ... | ... |
| P1 | ... | ... |

## 4. 交互流程

...

## 5. 非功能需求

...

## 6. 开发建议

- 建议第一期实现：...
- 建议第二期实现：...
- 需预研：...
```
